# H0a — does one v2 host survive the hub's load? (#2046)

**Status: PRE-REGISTERED. Written and committed before any measurement.** Part of #2043; feeds the decision "one host, or one database per shard" and the frontdoor disposition (#2068).

## Question
v1 needed a three-shard pool, a Python frontdoor and a watchdog because one engine's event loop saturated under parallel load (nine restarts on 2026-10-04/05 killed every in-flight session on the shard). Does **one** host process running the opencode v2 server stay healthy under the same kind of load?

## Where it runs, and why
**On erlich** (24 threads, 62 GB), as its **own transient user unit** at lowered CPU priority, outside every hub shard's cgroup, on loopback ports 53000-53999, with temp XDG dirs and a fresh database. Not on the mini: it is a 10-core, 16 GB, 22 GB-free laptop-class machine that is in use, whose sleep setting would interrupt a multi-hour run, and a pass there would say less about the machine the host will actually run on. Cost to the hub: about 3 cores and 2 GB. Because erlich is shared and busy, **every measurement is paired with a control** (below) so machine noise is attributable.

## Load levels (derived from the hub's data, not guessed)
Read-only query of the hub database, last 14 days, message rows per session per minute (proxy; it sees completed writes only, so streaming and fan-out traffic are not visible and the proxy errs LOW):

| statistic | value |
|---|---|
| peak distinct sessions writing in one minute | **12** |
| p99 / p95 / p50 of that | 7 / 4 / 1 |
| peak messages per minute | **115** |
| p99 messages per minute | 33 |

- **L1 = observed peak:** 12 concurrent sessions, about 115 messages/min.
- **L3 = three times peak:** 36 concurrent sessions, about 345 messages/min.

## The driver (synthetic; the v1 API differs, so recorded traffic is not replayable)
Against a real host process (`packages/host`) with a **paced** loopback model (token frames spread over 2-8 s, because an instantaneous fake flatters the host) and no credentials:
- N concurrent sessions, each looping: create a session if needed, prompt, wait for the turn to finish, think-time 1-6 s.
- A tool-call turn every 5th turn (a permission-denied shell call, which exercises the permission path), a reasoning-bearing turn every 7th.
- 1 global `/api/event` subscriber and one per-session subscriber for a third of the sessions; 10 percent of subscribers abort and reconnect every few minutes.
- A periodic `GET /api/session` list and `/api/info` poll (the dashboards).
Each level runs **2 hours** after a 5-minute warm-up that is excluded.

## What is measured, and the controls
- **Host event-loop lag**: a probe inside the host process is not available yet (observability is #2065), so the harness measures it externally and conservatively as the **round-trip latency of `GET /amicode/ping` from a separate process**, every 250 ms, plus the host's own timer drift if the host exposes it. External ping latency is an upper bound on loop lag (it adds loopback and scheduler time).
- **Control**: the same probe against a trivial `Bun.serve` that does nothing else, in a separate process at the same priority, on the same machine, simultaneously. The **excess** of host latency over control latency is the host's own contribution; the control latency is the machine's.
- **Wedge**: the probe gets no response within 2 s on two consecutive ticks (the same definition the watchdog uses, "HTTP-silent for two ticks"), or the process exits.
- **Memory**: RSS of the host process every 10 s from `/proc`.
- Also recorded: turns completed and failed, event-stream disconnects, subscriber reconnects that lost frames, host CPU seconds, machine load average.

## Pass criteria (fixed now)
For **each** level, over the 2 h window after warm-up:
1. **Latency:** p99 of host ping latency **minus** p99 of control ping latency is **under 250 ms**, AND the host p99 itself is under 500 ms. (If the control's own p99 exceeds 100 ms, the run is **inconclusive** for latency and is repeated in a quieter window; it is not counted as a pass.)
2. **No wedge:** zero wedge events and zero unplanned process exits.
3. **Memory:** RSS growth from the end of warm-up to the end of the run **under 2 GB**, and the least-squares slope not extrapolating past 8 GB at 24 h.
4. **Correctness under load:** at least 99 percent of turns complete; no turn is silently lost (every started turn ends completed or failed visibly).
- **Decision rule:** all four at L3 ⇒ **one host** is viable; frontdoor behaviours are then judged on their merits (#2068). All four at L1 but not L3 ⇒ one host with a documented ceiling and a per-database shard plan beyond it. Fail at L1 ⇒ keep a pool: **one database per shard** (several v2 services on one database are unsupported).

## Limits of this experiment (stated now, not discovered later)
Synthetic traffic and a fake model: it does not exercise real provider latency, real tool I/O, subagent fan-out, large contexts or compaction. It cannot reproduce the v1 incident's exact trigger. It runs one host, not the fleet multiplexer. A pass is evidence that the *server* is not the bottleneck at hub-scale concurrency, not proof of production safety.
