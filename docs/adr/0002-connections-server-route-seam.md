# The Connections credential seam lives in the vendored app server, not the extension

Status: accepted (2026-07-19)

The Connections panel (credential entry + validation + status for Company Compute and Pasqal Cloud) is served by amicode-owned routes in the vendored opencode fork's server, which owns the credential store and validators and answers key entry synchronously in one round trip. The VSCode extension is a consumer, not the owner.

**Why:** three candidate seams were developed and judged (security / UX-consistency / maintainability panel, 2026-07-19). The server-route seam won because (1) it extends two live fork patterns — the fork server already writes `~/.amico` in-process and already spawns external CLI children with timeout handling (the vault-status relay); (2) key entry works under standalone `opencode serve` with no extension — the best CLI/headless parity; (3) UX is one awaited POST — "validating…" is the in-flight fetch, the result arrives in the same round trip, versus the runner-up's structural double-poll; (4) it moves Pasqal secret handoff out of the agent's bash transcript (today the spike's credential protocol has the agent set the password on its own command line — `ps`-visible, in a persisted transcript).

**Conditions of merge (the hardening grafts):** per-boot random server password injected at spawn (route auth is otherwise a verified no-op and any localhost page could drive the routes); mutation routes refuse to serve when the server is bound beyond loopback; minimal env for spawned validator children (never a full env spread); atomic + `0600` at file birth with mode-at-birth tests (ADR 0001 is the governing at-rest discipline); mtime-based staleness with background revalidation (hand-edited `cloud.json` is a supported flow); offline renders "last verified as <identity>", never a false invalid, and submitter drift renders as an explicit diff; golden fixtures lock the two cross-repo contracts (the `cloud.json` byte shape parsed by the real CLI reader, and the Pasqal validator's exit-code/stdout contract).

**Flip condition (recorded verbatim from the judgment):** revisit toward the runner-up (extension-owned store with a file seam) if the per-boot password graft is rejected, if the server must stay bindable beyond loopback with credential routes live, or if a VSCode SecretStorage/keychain migration firms up — the fork-resident store is unreachable from extension APIs.

**Accepted costs:** validation logic lives in the vendored binary (urgent fixes are rebuild + re-vendor, not an extension patch); the fork's route-registration file is the highest-conflict spot on upstream rebases; `cloud.json` has multiple uncoordinated writers (fork server, the in-flight `setCloudKey` command pending merge, hand edits) — last-writer-wins, detected by staleness, not prevented.

**Considered:** file seam — extension owns store, fork writes ephemeral request files, poll-watcher ingest (runner-up: best raw security, but structural 1–2s feedback latency, a bespoke two-repo secret protocol, and no standalone-serve path); loopback bridge — extension HTTP listener the fork proxies to (rejected: mints a new secret and an unprecedented listener, worst CLI parity, only candidate with a cross-user port-squat theft path).
